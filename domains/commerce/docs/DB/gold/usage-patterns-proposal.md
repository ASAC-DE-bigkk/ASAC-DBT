# usage_patterns 표현력 — 마켓플레이스 역제안 + commerce 백로그

commerce D1 서빙 22종에 대해 "이 데이터로 실질적으로 가능한 질의 패턴"을 전수 설계·검증하는
과정(ASAC-DBT#471)에서, 현재 게이트웨이(ASK-Seoul-Serving `run_pattern`) 계약으로는 표현할 수
없는 질문 **94건**을 수집했다. 이 문서는 그 94건을 세 갈래로 나눈다:

- **(A) 이미 관용구로 해결** — 게이트웨이 변경 불필요. 규약(표기 규칙)에 편입만 한다.
- **(B) commerce 자체 숙제** — 게이트웨이 문제 아님. gold/서빙 스키마 확장으로 해결(별도 백로그).
- **(C) 게이트웨이 계약 변경 필요** — 마켓플레이스에 내는 역제안(P1~P8).

역제안은 (C)뿐이다. **(B)를 역제안 이슈에 섞지 않는다.** 근거는 게이트웨이 코드
(`serving/index.js` `handleRunPattern` 569~668)와 2026-08-08 실 D1 실측이다.

> 함께 읽기: 표기·보안 규약은 [usage-patterns-convention.md](usage-patterns-convention.md),
> 조합 관용구 카탈로그는 그 §4, 패턴 목록은 [usage-patterns-catalog.md](usage-patterns-catalog.md).

## 0. 요약

- 94건 중 **역제안(C)은 소수**(약 30건, 8개 제안 P1~P8). 최다 주제였던 "배열 IN"(~21건)은
  `json_each` 관용구로 **게이트웨이 변경 없이 이미 열렸다**(A). 시간축·분위수·지역축·인구
  정규화 등 **약 43건은 게이트웨이가 아니라 commerce gold/서빙 스키마의 숙제**(B)다.
- 8개 제안 중 **7개는 인젝션 표면을 늘리지 않는다** — 값 슬롯(기본값·배열·함수)이거나 결과
  변형(피벗·페이지네이션)이라 "소비자가 SQL을 짓는" 여지가 없다. 진짜 위험 확장은 **하나뿐**
  (식별자 슬롯 P6)이고, 그것조차 화이트리스트+치환후재파싱으로 닫힌다.
- 따라서 **"AI 접근 폭 확장 vs 안전"은 트레이드오프가 아니다**(§4). 표현력은 게시자가 짓고
  검증한 패턴의 어휘를 넓히는 것이지 소비자에게 질의 조립권을 주는 것이 아니며, 게시 전 정적
  감사(convention §6)가 확장의 경계를 그대로 정의한다.
- 핵심 역제안은 P0: **게이트웨이가 테이블 allowlist를 직접 강제**하면, 지금 commerce 측
  감사에만 의존하는 테이블 스코프 방어가 게이트웨이 자체 방어로 승격된다(§3.0).

| 가용 | 불가 |

## 2. (A) 이미 되는 것 — 규약화만

### A1. 배열 IN — `json_each` (실 D1 검증)

```sql
-- :gus = '["11680","11650","11710"]'   (JSON 배열 "문자열" 파라미터)
SELECT gu_code, SUM(cnt) AS n
FROM   d1_flow_monthly
WHERE  gu_code IN (SELECT value FROM json_each(:gus))
GROUP  BY gu_code;
```

`:gus`는 단일 문자열 스칼라라 게이트웨이 `:name → ?` 값 bind를 그대로 통과하고, 배열 전개는
SQLite `json_each`가 SQL 안에서 한다. **게이트웨이 계약 무변경.** 정적 감사기가 `json_each`만
테이블값 함수 화이트리스트에 넣는다(`pragma_*`는 차단 유지). 파싱 실패 시 0행(조용한 실패,
주입 아님). 잔여 개선(검증·상한·가독성)은 P3에서 규약화 제안.

### A2. 하버사인 반경 — `sqrt`/`cos`/`radians` (실 D1 검증)

격자 중심점 위경도로 근사 반경 필터가 SQL 안에서 표현된다. 별도 지오 확장 불필요. 정밀 폴리곤·
행정구역 매핑은 (B6).

## 3. (C) 게이트웨이 역제안 (우선순위: 낮은위험·높은효용 순)

### P0 (전제) — 게이트웨이가 테이블 allowlist를 직접 강제하라

지금 게이트웨이는 저장 SQL을 공유 D1 전체에 verbatim 실행하며 **어느 테이블을 읽는지 검사하지
않는다**(`index.js:647`). `_keys`(API 키 해시)·`_usage`·타 도메인 `d1_*`가 같은 DB에 있어,
어느 도메인이 감사를 우회한 패턴을 게시하면 `_keys` 유출을 게이트웨이 코드가 막지 못한다. 지금
그 방어는 오직 도메인 오너의 게시 전 정적 감사(convention §6)에만 있다. **게이트웨이가 제품별
소유 테이블 allowlist를 직접 강제**하면 그 방어가 게이트웨이 자체 방어로 승격되고, 그 위에서
P1~P8을 여러 도메인에 걸쳐 안전하게 열 수 있다. 확장과 방어 강화는 한 묶음이다.

| 순위 | 제안 | 위험 | 효용 | 인젝션 표면 | 비고 |
|---|---|---|---|---|---|
| P1 | 선택 파라미터+기본값 | 0 | 높음 | 증가 없음 | 즉시 채택 후보 |
| P2 | run_pattern 페이지네이션(커서) | 낮음 | 중간 | 증가 없음 | `handleData`에 코드 이미 존재 |
| P3 | 배열 파라미터 1급 선언 | 낮음 | 높음 | 증가 없음 | json_each로 당장 됨→규약화 |
| P4 | 함수 화이트리스트 **문서화** | 낮음 | 중간 | 거의 없음 | 대부분 실측으로 이미 가용 |
| P5 | 서버측 동적 피벗(long→wide) | 낮음 | 중간 | **없음(SQL 불변)** | 결과 변형 책임 신규 |
| P6 | 화이트리스트 식별자 슬롯 | **높음** | 최고 | **증가(치환)** | 3중 방어 필수·P0 선행 |
| P7 | 크로스 참조 JOIN allowlist | 중간 | 중간 | 증가(테이블) | (B5)가 더 안전 |
| P8 | 패턴 체이닝/파이프라인 | 중간 | 높음 | 조건부 | 복잡도 최고·(B)로 상당 해소 |

**P1 선택 파라미터+기본값** — 패턴 메타에 `param_defaults`(선택) + `param_enum`(선택). 미전달
파라미터를 게시자 선언 상수로 bind. 값 bind라 인젝션 표면 0. 오히려 enum 검증이 센티널 오타의
조용한 0행을 400으로 잡아 안전을 높인다.

**P2 페이지네이션** — `handleData`의 커서 페이지네이션(`has_more`/`next_cursor`)이 이미 있는데
`run_pattern`에만 빠졌다. 발행 결속 키셋 커서, 페이지당 쿼터 1건. offset 아님(재적재 중 부정확).

**P3 배열 파라미터** — `{type:"array", item:"string", max_len:N}` 선언 → 게이트웨이가 `?,?,?`
전개. 각 원소는 값 bind라 인젝션 불가. json_each 대비 이점: 명시 검증·`max_len` 상한·감사기
구조 인식. json_each로 당장 되므로 급하지 않음.

**P4 함수 화이트리스트 문서화** — 실측상 `sqrt/pow/cos/radians/abs/round/instr` 가용. 게이트웨이
계약(llms.txt)에 **보장 함수를 명문화**하면 게시자가 근사식을 버리고 정식 지표를 쓴다. `REGEXP`·
`stddev`/`corr` 집계는 불가 확정 → (B)로. 대부분 구현이 아니라 문서화.

**P5 동적 피벗** — 패턴 메타에 피벗 스펙, 게이트웨이가 롱 결과를 와이드로 후처리. **SQL 불변 →
인젝션 표면 없음**. `max_cols` 상한. 게이트웨이가 결과를 변형하는 신규 책임.

**P6 식별자 슬롯 (유일한 진짜 위험 확장)** — `@{order_col}` 식별자 전용 슬롯 + **필수
화이트리스트**. 화이트리스트 없으면 `order_col="(SELECT key_hash FROM _keys LIMIT 1)"`로 유출
통로가 된다. 3중 방어 계약 강제: ① 게이트웨이가 `allow` 미선언 슬롯 실행 거부(P0), ② 정확
문자열 일치만(부분일치·정규식 금지), ③ 치환 후 정적 감사 재파싱. **화이트리스트가 표현력(허용
컬럼)과 안전(그 외 거부)을 한 메커니즘으로 함께 정의** — 넓힐수록 감사가 그만큼 따라붙는다.
P1~P5 실증 후 P0 선행하에 마지막에 연다.

**P7 크로스 참조 JOIN allowlist** — 인구/유동인구 정규화용. 위협 (b) "타 도메인 참조"를
의도적으로 좁게 여는 것. **차선책** — 더 안전한 길은 (B5) commerce gold에 인구 사전결합.

**P8 패턴 체이닝** — 검증된 저장 패턴들을 오케스트레이션(`run_pipeline`), 1단계 결과 컬럼을
2단계 배열 파라미터(P3)로 이월. 각 단계 개별 검증. MCP stateless 원칙과 긴장 최대 → 단일 요청
내 다단계로 제한. **(B) 사전조인 서빙 테이블로 상당수 해소** → 진짜 동적 케이스만 마지막에.

각 제안의 계약 인용·API 스케치·보안 영향 상세는 이슈 본문에 첨부한다.

## 4. 당위성 — "확장 vs 안전"은 트레이드오프가 아니다

게이트웨이 안전 모델은 "소비자가 SQL을 짓지 못한다"이다(`index.js:563` "질의를 '짓는' 여지가
없다"). P1~P5·P7~P8은 이 원칙을 하나도 깨지 않는다 — 값 슬롯을 늘리거나, 결과를 변형하거나,
검증된 패턴을 잇는다. 소비자에게 질의 조립권을 주지 않는다. 표현력이 느는 주체는 소비자가
아니라 **게시자의 패턴 어휘**다.

진짜 위험 확장은 P6 하나인데, 그것도 트레이드오프가 아니다 — 화이트리스트가 표현력과 안전을
**동시에** 정의하기 때문이다. `allow:["lq","share"]`는 "이 둘로 정렬 가능"(표현력)이자 "그 밖은
400"(안전)이다.

**표현력을 좁혀도 새 안전이 생기지 않는다.** 값은 이미 안 새고(decision/0001), 테이블 스코프는
정적 감사가 지키며, 자원은 쿼터·버스트·MAX_LIMIT이 막는다. 이미 겹겹이 좁은 데이터(사전집계
스냅샷·값최소화·공개 옵트인·일일 쿼터)에 표현력까지 좁히면 효용만 깎일 뿐이다 — 순손실이다.
안전은 기능을 **막아서**가 아니라 감사가 **강제해서** 온다.

## 5. (B) commerce 후속 백로그 (역제안 이슈에 섞지 말 것)

게이트웨이 문제가 아닌, commerce gold/서빙 스키마의 숙제. 별도 백로그로 관리한다.

- **B1 코드→이름 dim 테이블** — 자치구 코드-명 `d1_*` 배포. 계약7 교차 JOIN이 이미 열려 있어
  매핑 테이블만 있으면 `x_` 패턴으로 즉시 조인(전 지역축 제품 공용, 가치 높음).
- **B2 시간축(y/ym)** — gold를 스냅샷 일자/연도 파티션으로 append 적재. 기존 BETWEEN 관용구가
  그대로 시계열화(게이트웨이 무변경). ~13건.
- **B3 분위수/히스토그램 컬럼** — gold 집계에 p25/p75/p90·구간 버킷 사전 계산. 원자 레코드
  소실이라 D1 내 재계산 불가 — 상류에서 해결. ~7건.
- **B4 지역축(gu/dong)** — gold 재집계에 gu_code/admin_dong_code 축 추가 → 계약7 교차 JOIN으로
  지역×지표 패턴 일가. ~10건.
- **B5 인구/유동인구 기준표** — 인구 스냅샷을 commerce gold에 사전결합해 d1_*로 서빙(P7보다
  안전 — 계약 무변경).
- **B6 격자→행정구역 매핑** — `d1_geo_grid_to_gu`(격자 중심점→구/동) 서빙 → 폴리곤·행정 리포트.
- **B7 데이터 모델 결측** — 상태 전이쌍 집계 모델, 생존율 분모(개업/영업중 모수), 세그먼트 교차
  그레인, 3축 사전조인 테이블. 원천 그레인 소실이라 gold 상류에서 추가.
- **B8 REGEXP 업태 검색** — D1 REGEXP 부재 확정. FTS 검토 또는 `instr` 다중 키워드로 대체.

## 6. 열린 질문 (역제안 이슈 제출 전)

1. **게이트웨이 소유권(P0/P6)** — 테이블 allowlist·식별자 화이트리스트 강제는 ASK-Seoul-Serving
   코드 변경(공유 인프라). 어느 저장소 이슈로 누구에게, 조율 절차 확정 필요.
2. **식별자 슬롯 문법(P6)** — `@{name}`이 기존 `:name` 값 슬롯 정규식(`index.js:617`)과 충돌
   안 하는지 게이트웨이 팀 검토.
3. **파이프라인 vs stateless(P8)** — MCP stateless(`mcp.js:6`) 하에서 다단계를 단일 요청으로
   제한할지, 결과 핸들 허용 시 키별 격리·TTL·쿼터 회계 설계.
4. **P7 vs B5** — 인구 정규화를 게이트웨이 참조 JOIN(P7)으로 열지 commerce gold 사전결합(B5)으로
   닫을지 — 후자가 더 안전, commerce 적재 부담. 팀 결정.
